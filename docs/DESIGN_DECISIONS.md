# 设计决策说明

本文记录 lawyerAgents 在法律 RAG Agent 方向上的关键设计取舍。目标不是证明每个模块都“更先进”，而是说明为什么这些模块适合当前项目的法律问答、案情分析、文书生成和评测反馈闭环。

## 1. 为什么不用纯向量检索

法律问题里有大量必须精确命中的信息：

- 法律名称，例如《劳动合同法》《民法典》《刑法》。
- 条号、款号和司法解释编号。
- 罪名、案由、时效、程序节点。
- 用人单位、仲裁、起诉、报警等场景关键词。

纯向量检索擅长语义相似，但不稳定保证精确词项命中。比如用户问“劳动合同法第十九条”，系统应优先找到第十九条，而不是找到一段语义上类似的试用期说明。

因此项目没有把向量检索作为唯一入口，而是把它作为混合召回的一路。

## 2. 为什么使用 BM25 + Vector + RRF

BM25 和 Vector 解决的问题不同：

- BM25 负责精确召回，适合法条编号、法律术语、罪名和时效关键词。
- Vector 负责语义召回，适合口语化案情和用户表达不规范的问题。
- RRF 用排序名次融合两路结果，避免直接比较 BM25 分数和向量相似度这种不稳定操作。

RRF 的价值在于它不要求两种检索分数处于同一尺度，只关注“这个候选在各路检索里排得是否靠前”。这对法律 RAG 很实用，因为召回阶段的目标是尽量把可能相关的依据放进候选池，后续再用 Rerank 控制质量。

## 3. 为什么需要 Rerank

混合召回会扩大候选范围，但候选越多，噪声也越多。法律场景中，无关条文进入上下文会带来两个风险：

- 模型引用了看似相关但实际不适用的法条。
- 多个法律领域混在一起，导致回答结论偏移。

Rerank 的作用是对 RRF 后的候选进行相关性重排，只让更高质量的片段进入最终上下文。它也能帮助控制 token 成本和响应延迟。

项目保留 `ENABLE_RERANK`、`RERANK_TOP_K`、`RERANK_FINAL_K` 等配置，是为了在质量和速度之间做可调取舍。

## 4. 为什么法律场景必须做引用校验

普通 RAG 可以接受“答案大体正确但引用不完整”；法律 RAG 不行。法律问答的风险往往出现在引用层：

- 编造不存在的法律名称。
- 编造条号。
- 把条文内容说错。
- 引用的 `sources` 与正文依据不一致。

因此项目把 `sources` 和引用校验作为一等输出。评测脚本中的 `citation_supported_rate` 会检查回答正文里的显式“法名 + 条号”引用是否能在返回来源中找到。

引用校验不能证明法律结论一定正确，但它能低成本发现一类非常危险的问题：回答看起来像法律意见，实际没有来源支撑。

## 5. 为什么用 LangGraph 做多域拆解

法律案情经常跨领域。例如：

- 劳动争议 + 刑事报案。
- 合同纠纷 + 公司治理。
- 婚姻家庭 + 治安处罚 + 民事赔偿。

如果只按一个主领域检索，系统可能漏掉次要但关键的法律路径。项目用 LangGraph 实现两种路径：

- 单域快速路径：直接检索和生成，降低延迟。
- 多域协作路径：分类后生成子问题，对每个领域并行检索，再合并上下文。

这种结构比在一个大 prompt 里要求模型“自己想全”更可控，也更容易从 SSE 和评测结果里定位是分类错了、某个领域没召回，还是合并后被挤掉。

## 6. 为什么 SSE 展示 RAG 过程

法律 RAG 的用户等待时间可能来自多个阶段：分类、改写、BM25、向量检索、RRF、Rerank、上下文扩展、引用校验和生成。如果只返回最终答案，用户和开发者都不知道系统在哪里耗时或失败。

项目通过 SSE 暴露：

- `meta`：意图、领域、缓存、多域、文书类型等元信息。
- `substep`：每个 RAG 阶段的进度和耗时。
- `token`：模型生成的正文。
- `done`：最终结构化结果。
- `error`：失败步骤和可读错误。

这既改善前端体验，也让调试和面试演示更清楚：可以直接看到系统不是“黑盒聊天”，而是在执行可追踪的 RAG pipeline。

## 7. 为什么缓存要区分任务类型

项目有三类任务，返回结构并不相同：

- 法条问答主要返回 `answer`、`sources`、`risk_warning`。
- 案情分析还需要返回 `case_state`、`analysis_result`、`case_analysis_id`。
- 文书生成还需要返回 `document_result`、`missing_fields`、`status` 等。

如果所有任务共用同一种问答缓存，旧的 QA 缓存可能覆盖新的案情分析或文书生成请求，导致结构化状态丢失。当前流式入口会先做 intent detection，并对 `analysis`、`document` 任务避开普通语义缓存，以保证这些任务能返回完整的结构化 payload。

因此缓存策略必须按任务类型区分：QA 可以更积极缓存，案情分析和文书生成需要优先保证状态正确。

## 8. 为什么案情分析同时返回 Markdown 和结构化 JSON

案情分析需要服务两类消费方：

- 人阅读：Markdown 报告更适合解释案情摘要、风险、证据和处理路径。
- 系统复用：前端卡片和文书生成需要稳定字段，例如 `case_summary`、`risk_level`、`claims`、`evidence_checklist`、`missing_information`、`document_suggestions`。

如果只返回 Markdown，前端只能按标题切块，后续文书生成也难以可靠复用 claim、证据缺口和下一步动作。如果只返回 JSON，用户阅读体验又会变差。

因此当前案情分析 Prompt 要求模型先输出固定 Markdown 报告，再追加 JSON 代码块。后端会解析 JSON 生成 `analysis_result`；如果 JSON 异常，会记录 `warnings` 并继续返回 Markdown，避免结构化解析失败影响主回答。

## 9. 为什么案例库不能和现行法条同等权重

案例对法律分析有参考价值，但不能和现行法条同等处理：

- 法条和司法解释是规范依据，案例多是裁判参考。
- 案例事实差异很大，低相关案例会误导用户。
- 旧案例可能受法律修订、地区口径和个案事实影响。
- 用户容易把“相似案例”误解成“必然结果”。

因此项目把官方精选案例作为按需参考信息，而不是默认与主法条库同权进入答案依据。配置里也将案例检索设计为可开关、可限制 top_k 和 min_score 的独立模块。

对法律 RAG 来说，宁可少展示低相关案例，也不要为了凑来源数量把不适用案例放进回答。

## 10. 对当前能力边界的说明

当前项目已经实现法条问答、案情分析、SSE 可观测、轻量评测和劳动人事争议仲裁申请书生成闭环。需要注意：

- 文书生成当前重点不是全类型法律文书平台，而是劳动仲裁申请书闭环。该链路采用“案情状态提取 -> 字段槽位检查 -> 缺失信息追问 -> 模板化生成”，不会让 LLM 直接一把生成最终文书。
- 劳动仲裁申请书字段会标记为 `known / missing / partial / uncertain`。核心字段缺失时暂停生成并最多追问 3 个问题；可暂缺字段会保留 `【待补充】` 占位。
- 评测脚本以规则评测和确定性指标为主，不等价于完整法律意见质量评审。
- 引用校验能发现正文引用是否被 sources 支撑，但不能替代律师审查。
- Java Spring Boot 网关属于 Roadmap，不是当前已完成能力。
